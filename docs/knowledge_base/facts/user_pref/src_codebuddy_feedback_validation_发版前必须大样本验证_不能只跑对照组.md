[src=codebuddy:feedback_validation] 发版前必须大样本验证（不能只跑对照组）
任何 SQL/标签/规则类产出，交付前必须做**结果集随机抽样验证**（≥10 样本），逐样本核对目标级数据+抽帧画面，给出明确的精度统计（真/弱/假 分类），再谈发版。

**Why:** 无保护左转 SQL 迭代中，我连续 4 个版本（v4~v7）只用固定 3-4 个对照 bag + 1-3 帧抽帧就交付，用户两次抽检发现大量误报并明确批评："你写完一个 sql 之后你自己会抽多少个来进行验证啊，我怎么感觉就抽了一个验证完就发我了"。固定对照组存在过拟合——每个对照 bag 都是上一轮修复的靶子。

**How to apply:**
- 对照组（回归测试）+ 结果集随机抽样（精度测试）分开做；抽样要覆盖不同时段/天气/bag 新旧（topic 命名不同）
- 抽帧注意：帧数要铺满事件全窗口（按事件时长自适应 fps，别让 2fps×12 帧只覆盖前 6 秒）；冲突时刻要对齐（最近接近时刻，别盲取首尾帧）
- 每个误报要归因到具体机制（如"单帧速度尖峰放行静止车"），用目标级数据（速度分布/朝向轨迹）证实或证伪，别只靠画面猜
- 交付时附精度统计和已知边界，让用户能快速复核

**【2026-08-19 追加】验证必须核对执行路径，不能只看输出内容。**

改链路/路由类代码后做 E2E，除了检查输出本身正确，还必须核对**该次请求实际走的代码路径**（route_method 字段、后端日志里的路径标记），确认没有被 fallback/兜底路径掩盖。

**Why:** 参考 SQL 模式改造后，我的两次 E2E 输出 SQL 都"看起来像对的"就宣布通过；实际是代码 100% 崩溃（TableInfo TypeError），全部降级到旧关键词路径产出的 SQL。用户自己跑遇到校验警告才暴露。输出正确 ≠ 路径正确——兜底路径恰恰会产出合理输出，是最危险的掩盖方式。

**How to apply:** E2E 验证 checklist：① 输出内容正确；② route_method/日志确认走的是新路径；③ 日志无降级/异常警告；④ 对照组（不应受影响的 case）也走新路径且行为不变。四条齐了才算验证通过。
