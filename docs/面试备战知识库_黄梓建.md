### 1.2 核心数据结构详解

#### concept_groups.yaml（概念组）

这是Round 1 LLM的"知识源"，告诉LLM有哪些概念可用：

```yaml
concept_groups:
  掉头:
    nl_variants: [掉头, 路口掉头, U型掉头, 掉头转弯]  # 用户可能的说法
    query_table: range_tag                           # 查哪张表
    tag_names: [INTERSECTION_UTURN]                  # 对应的tag_name
    tag_patterns: []                                 # LIKE模式(车端标签)

  红绿灯:
    nl_variants: [红绿灯, 交通灯, 信号灯]
    query_table: range_tag
    tag_names:
      - TrafficLightAbnormal
      - RunRedLight
      - CrossStopLineOnYellowLight
      - GreenLightNotProceeding
      - STOPANDGO_FIRSTCARSTOPATREDLIGHT
      - STOPANDGO_FIRSTCARSTARTATGREENLIGHT
    tag_patterns: []
```

**关键设计点：**
- `nl_variants`：同一个概念，用户可能有多种说法。LLM不需要理解"掉头"="U型掉头"，查表即可
- `tag_names`：一个概念可能对应多个tag_name（如"红绿灯"对应6个tag）
- `tag_patterns`：支持LIKE模糊匹配，如`INTERSECTION_%`可以匹配INTERSECTION_STRAIGHT/LEFTTURN/RIGHTTURN/UTURN
- `query_table`：标明这个概念查哪张表，决定后续JOIN方式

#### schema_dictionary.yaml（Schema字典，2228行）

由`derive_schemas.py`从`schema_master_raw.yaml`（母表）自动派生，包含每个tag/字段的语义描述：

```yaml
tags:
  AbnormalLaneChange:
    description: 异常变道行为
    source: cloud_operator
    operator: AbnormalLaneChange
    operator_path: L2_Pred/rule_based_mining/.../op_abnormal_lane_change.py
    related_tables: [range_tag]

  AvoidanceBorrowLane:
    description: 自车借用左右车道避让前方障碍物后返回原车道
    sub_tags: [AvoidanceBorrowLaneLeft, AvoidanceBorrowLaneRight]
    limitations:
      - 仅在雨刮器启动时触发，不记录关闭状态
    related_tables: [range_tag]
```

**用途**：当LLM需要理解某个tag_name是什么意思时，从dictionary中检索description。比如LLM不知道`GreenLightNotProceeding`是什么，查字典得到"绿灯亮起后车辆未及时起步通行"。

#### Block YAML（12种可复用CTE Block）

每个Block是一个参数化的CTE模板：

```yaml

name: event_extraction

parameters:
  tag_name:
    type: string
    required: true
    description: "range_tag中的tag_name"
    examples: ["CrossConflict", "VRUCrossConflict"]
  pre_pad:
    type: float
    default: 2.0
    description: "start_ts前扩秒数"
  post_pad:
    type: float
    default: 2.0
    description: "end_ts后扩秒数"
```

#### Recipe YAML（68种场景配方）

Recipe编排Block序列 + 定义variant（变体）：

```yaml
# conflict_pipeline.yaml
name: conflict_pipeline
description: 完整的冲突检测流水线

blocks:
  - name: event_extraction
    cte_name: "{tag_prefix}_events"
    params:
      tag_name: "{tag_name}"
      pre_pad: 2.0
  - name: ego_speed_analysis
    cte_name: "EgoSpeedAnalysis"
    upstream: "{tag_prefix}_events"
  - name: proximity_analysis
    cte_name: "{ProximityCTE}"
    upstream: "EgoSpeedAnalysis"
  - name: conflict_classification
    cte_name: "WithConflictResult"
  - name: duration_filter
    cte_name: "final_events"
  - name: event_merge
    cte_name: "merged"

variants:
  vehicle:                    # 他车冲突
    tag_name: CrossConflict
    tag_prefix: cross
    target_type: vehicle
  vru:                        # 行人/非机动车冲突
    tag_name: VRUCrossConflict
    tag_prefix: vru_cross
    target_type: vru

final_select_template: |
  SELECT '{output_tag_name}' AS tag_name,
         merged_start AS start_ts, ...
```

**Block拼装流程（代码级）：**
1. `BlockAssembler.assemble(recipe_name, variant_name, extra_params)`
2. 加载Recipe → 获取variant的默认参数
3. 合并extra_params（来自NL理解，如用户指定的距离阈值）
4. 逐Block展开：
   - `custom` Block：直接用inline `sql_template`
   - 标准Block：从BlockLibrary加载 → 合并参数 → `{{param}}`替换
5. 参数交叉引用解析（`_resolve_dict_vars`，支持`{tag_prefix}_events`这种嵌套变量）
6. 拼接所有CTE → 加final_select → 输出完整SQL

**Fast Path优化**：部分Recipe的variant包含`raw_sql`字段（300+行的生产SQL），Block拆解无价值时直接透传，跳过Block拼装流程。

### 1.3 Self-Correction机制（代码级详解）

```python
# agent_engine.py 核心逻辑
MAX_CORRECTIONS = 3  # 可通过环境变量配置

for attempt in range(MAX_CORRECTIONS + 1):
    ok, err_msg = self._dry_run(sql)  # SQLite EXERGY试编译
    if ok:
        break  # 语法通过，执行
    
    correction_rounds += 1
    if correction_rounds >= MAX_CORRECTIONS:
        return AgentResult(
            error=f"经{MAX_CORRECTIONS}次纠错仍未修复",
            max_corrections_exceeded=True
        )
    
    # 构建纠错Prompt
    correction_messages = self._build_correction_prompt(sql, err_msg, schema_text)
    raw_sql = await self.llm.chat(
        correction_messages[0]["content"],  # system: 语法规则+schema
        correction_messages[1]["content"],  # user: 报错信息+原SQL
        temperature=0.0  # 确定性输出
    )
    sql = self._clean_sql(raw_sql)  # 去markdown标记等
```

**_build_correction_prompt的内容：**
- System: SQLite语法规则提醒（时间字段单位、json_extract用法、CASE必须有END等）+ 相关表结构
- User: 语法错误信息 + 原始SQL + "请修正SQL"

**_dry_run的实现：**
```python
def _dry_run(self, sql: str) -> Tuple[bool, str]:
    try:
        conn = sqlite3.connect(":memory:")
        conn.execute("CREATE TABLE ...")  # 创建临时表
        conn.execute(f"EXPLAIN {sql}")
        conn.close()
        return True, ""
    except Exception as e:
        return False, str(e)
```

**实际纠错统计**：
- 90%的语法错误在1轮内修复（常见：列名拼错、缺少END、JSON提取语法）
- 8%在2轮内修复（复杂CASE WHEN嵌套错误、CTE引用链断裂）
- 2%超过3轮放弃（通常是Schema不匹配，需要Schema Sync）

### 1.5 必考追问 & 标准回答

**Q: 为什么不用端到端LLM直接生成SQL？**

端到端生成在简单查询（Spider数据集，<10表）上效果不错，但我们的场景有三个致命差异：

1. **Schema规模**：30+表、200+字段，远超Spider的规模。LLM在超宽Schema下容易搞混字段归属（比如"掉头"该查link_type还是link_turn_type）
2. **SQL复杂度**：不是简单的SELECT-WHERE，而是多层CTE + gaps-and-islands + -1前向填充，单条SQL动辄200+行。端到端生成这种复杂度的SQL，语法错误率>40%
3. **可重复性**：同样的问题，端到端LLM每次生成不同SQL，无法回归测试。两阶段架构保证同一问题→同一Recipe→同一SQL（确定性）

两阶段的本质是：**把"理解意图"（高容错）和"生成代码"（零容错）解耦**。Round1做分类（即使错一个概念也不影响整体），Round2做模板拼装（语法100%正确）。

**Q: Block和Recipe的关系？用一个完整例子说明？**

Block是可复用的CTE片段，Recipe是Block的编排序列。

以"他车横穿冲突"为例：
```
Recipe: conflict_pipeline, Variant: vehicle

Block序列：
1. event_extraction(tag_name=CrossConflict, pre_pad=2.0, post_pad=2.0)
   → 从range_tag提取CrossConflict事件，时间窗口前后各扩2秒
   → 输出CTE: cross_events(start_ts, end_ts, param, agent_id, ...)

2. ego_speed_analysis(upstream=cross_events)
   → 在事件时间窗口内关联ego表，计算自车速度变化
   → 输出CTE: EgoSpeedAnalysis(ts, speed, accel, ...)

3. proximity_analysis(upstream=EgoSpeedAnalysis, target_type=vehicle)
   → 关联dynamic_obj，筛选冲突目标物，计算距离/方位
   → 输出CTE: CrossProximity(obj_id, dist_x, dist_y, type, ...)

4. conflict_classification(speed_cte=EgoSpeedAnalysis, prox_cte=CrossProximity)
   → 综合速度变化+目标距离，判定冲突类型(横向/纵向/对向)
   → 输出CTE: WithConflictResult(conflict_result, severity_level, ...)

5. duration_filter(upstream=WithConflictResult, filter_mode=vehicle)
   → 过滤持续时间<3s的短事件（可能是误检）
   → 输出CTE: final_events

6. event_merge(upstream=final_events)
   → 合并时间上相邻的事件段（间隔<2s的合并为一段）
   → 输出CTE: merged(start_ts, end_ts, ...)
```

新增场景（如"左转冲突"）只需新建Recipe+Variant，复用已有Block：
```yaml
# turn_conflict_pipeline.yaml
variants:
  left_turn:
    tag_name: INTERSECTION_LEFTTURN
    tag_prefix: left_turn
    target_type: vehicle
```

**Q: 68%的查询走Recipe，剩下的32%呢？**

实际统计：
- 68%查询命中Recipe → Block拼装（确定性SQL，无需LLM生成）
- 22%查询走fallback → LLM端到端生成 + Self-Correction纠错
- 10%查询无法回答（Schema中不存在对应字段）

fallback的场景通常是：用户问了一个全新的组合方式，还没有对应Recipe。这时候退化为端到端LLM生成，但仍有Self-Correction保底。

**Q: 为什么Schema要分母表/结构/字典三层？**

这是v2.0的关键设计：

| 文件 | 角色 | 谁维护 | 用途 |
|------|------|--------|------|
| schema_master_raw.yaml | 母表（唯一权威源） | 人+脚本 | 包含所有枚举值、来源标注、语义描述 |
| schema_structure.yaml | 派生：表结构 | 自动生成 | 给LLM看：表名、列名、列类型、enum值 |
| schema_dictionary.yaml | 派生：语义字典 | 自动生成 | 给LLM看：tag/字段的中文描述 |

原因：人只维护母表一份文件，structure和dictionary自动派生。如果Schema变了（新增tag），只需改母表，运行`derive_schemas.py`即可。避免三份文件不同步的问题。

**Q: concept_groups和schema_dictionary的关系？**

- concept_groups：NL概念 → tag_name 的桥梁（用户视角）
- schema_dictionary：tag_name → 语义描述 的字典（系统视角）

举例：用户说"掉头"
1. concept_groups: "掉头" → tag_name: INTERSECTION_UTURN
2. schema_dictionary: INTERSECTION_UTURN → "路口掉头场景"

两者配合：Round1用concept_groups做概念识别，Round2用schema_dictionary做Prompt填充。

**Q: 动态Schema裁剪具体怎么做的？**

Round1识别出概念后，只注入相关表和字段：

```
用户: "帮我找掉头时自车速度骤降的场景"

Round1输出:
  concepts: ["掉头"]
  composition: "tag_join_ego"
  ego_fields: ["speed", "acceleration_longitudinal"]

Schema裁剪:
  - range_tag表: 注入完整结构(必须)
  - ego表: 只注入ts, speed, acceleration_longitudinal 3个字段
  - 其他表: 完全不注入
  → Prompt从全量8K tokens降至1.5K tokens
```

实现方式：`schema_reader.py`的`format_schema_for_prompt()`接受一个`required_tables`参数，只格式化指定表的指定字段。

**Q: 多模态校验具体流程？**

```
1. SQL执行 → 得到结果DataFrame
2. 取前20行 → 用前端渲染为HTML表格
3. Playwright无头浏览器截图 → 得到结果截图PNG
4. 发送给Vision模型(Kimi Vision):
   System: "你是SQL查询结果校验器"
   User: 
     "用户原始问题: [question]
      生成的SQL: [sql]
      查询结果截图: [image]
      判断: SQL是否正确回答了用户的问题？
      如果不正确，指出问题并给出修正建议。"
5. Vision模型返回:
   - 正确: "SQL正确地返回了掉头冲突事件的起止时间"
   - 错误: "SQL查的是link_type而非link_turn_type，应改为..."
6. 如果判断为错误 → 修正建议回注Prompt → 重新生成SQL
```

**Q: -1前向填充是什么？为什么需要？**

ego每一帧的`ego_static_map_link_id`是地图匹配结果。匹配可能短暂失败（GPS漂移、地图覆盖不全），此时值为-1。如果直接用-1去JOIN static_link，这帧就丢了。

填充规则：连续≤2帧-1 → 用前一帧有效link_id补；>2帧 → 保持-1不补。

逻辑：丢1-2帧大概率还在同一条路上，补上合理；连丢3帧以上说明真离开了，猜了反而错。

SQL实现（5层CTE）：
1. `ego_marked`：标记每段连续-1的起始帧
2. `ego_grouped`：SUM累积求和，给每段-1分配group_id
3. `ego_group_size`：COUNT(*)算每段-1有几帧
4. `ego_filled`：关联group_size + 取前一帧有效link_id
5. `ego_final`：CASE WHEN ≤2帧→补 ELSE →保持-1

**Q: gaps-and-islands是什么？**

SQL经典模式，用于把连续相同值的行分到同一组。

```sql
-- 示例：把1,1,1,0,0,1,1分成三组
SELECT is_uturn, MIN(ts) AS start_ts, MAX(ts) AS end_ts
FROM (
    SELECT ts, is_uturn,
           -- 每当值变化时seg_id+1
           SUM(CASE WHEN prev_val != is_uturn OR prev_val IS NULL 
                THEN 1 ELSE 0 END) 
               OVER (ORDER BY ts) AS seg_id
    FROM (
        SELECT ts, is_uturn, 
               LAG(is_uturn) OVER (ORDER BY ts) AS prev_val
        FROM ego_uturn
    )
)
GROUP BY is_uturn, seg_id
```

在我们的场景中，用于把连续的"掉头帧"聚合为一个完整事件段。

## 二、实例可控驾驶视频生成

### 2.1 方法架构图（面试画图用）

```
输入条件:
  首帧图像I₀ → VAE编码 → z₀ (条件潜变量)
  3D BBox序列 {B₁...Bₜ} → Box下采样器 → 结构化控制信号
  HDMap → BEV渲染 → 道路拓扑条件
  实例图像 {I_obj₁...I_objₙ} → 实例VAE管道

扩散去噪:
  噪声zₜ → UNet(含3种条件注入)
  ├── 1. 通道拼接: z₀ concat noise (首帧条件)
  ├── 2. Cross-Attention: CLIP(I_obj) → K/V (实例语义条件)
  └── 3. 通道融合: Instance VAE(I_obj, Bₜ) → 实例纹理条件

奖励反馈(ReFL):
  生成视频 ṽ → 裁剪实例 → CLIP特征
  真实视频 v → 裁剪实例 → CLIP特征
  Reward = cosine_sim(CLIP(ṽ), CLIP(v))
  L_total = L_diffusion + λ·L_reward  (仅在t∈[30,40])
```

### 2.2 必考追问 & 标准回答

**Q: 和DriveDreamer-2、GenAD的核心区别？**

| 维度 | DriveDreamer-2 | GenAD | 我们的方法 |
|------|----------------|-------|-----------|
| 控制信号 | BEV布局+文本 | BEV序列 | 首帧+3D Box+HDMap+实例图像 |
| 控制粒度 | 场景级 | 场景级 | **实例级** |
| 实例可控 | ✗（只能控制位置） | ✗ | ✓（CLIP引导+实例VAE+ReFL） |
| 跨帧一致性 | 一般（无实例约束） | 差（纯BEV预测漂移） | **强（"时空复制粘贴"+奖励）** |
| 训练策略 | 标准扩散损失 | GAN+MSE | **扩散损失+实例奖励联合优化** |

核心差异：我们实现了**实例级可控**——不仅控制"这里有车"，还能控制"这辆车的纹理和形状在所有帧保持一致"。

**Q: 实例相似度奖励反馈学习（ReFL）原理？**

分4步理解：

1. **为什么需要ReFL？**
标准扩散损失(Diffusion Loss)是像素级重建损失，它无法保证实例级语义对齐——模型可能生成一辆"位置正确但外观错误"的车，Diffusion Loss仍然很低。

2. **ReFL怎么做？**
- 从生成视频和真实视频的对应帧中，根据3D Box裁剪出实例区域
- 用CLIP ViT-L/14分别提取特征（512维向量）
- 计算余弦相似度作为奖励信号：R = cos_sim(f_gen, f_real)
- 奖励损失：L_reward = -log(R)（最大化相似度等价于最小化负对数相似度）

3. **为什么只在t∈[30,40]时间步优化？**
- SVD共有40个时间步（t=0完全去噪，t=40最噪声）
- t大（早期）：控制全局布局，修改会破坏场景结构
- t小（晚期）：只影响高频纹理细节，奖励信号太弱
- t∈[30,40]：语义和纹理的最佳平衡点，此时修改能同时影响外观和位置

4. **实例ID过滤是什么？**
只对首帧出现的实例计算奖励。原因：后续帧可能出现新实例（被遮挡后重新出现），这些实例没有对应的首帧参考，计算奖励会引入噪声。

**Q: "时空复制粘贴"VAE管道的技术细节？**

问题：实例在不同帧长得不一样（颜色变化、形状扭曲），这是SVD已知的缺陷。

解决方案：
1. 对每个实例，从首帧裁剪出实例图像（根据首帧3D Box）
2. 对未来第t帧，根据该帧的3D Box位置，用仿射变换（缩放+平移+旋转）将实例图像放到对应位置
3. 沿时间轴复制扩展：每一帧都有实例图像作为参考
4. 用VAE编码为条件潜变量（4D张量：batch×time×channel×spatial）
5. 在UNet中与噪声潜变量通道维拼接

为什么有效：VAE编码的实例潜变量提供了像素级纹理参考。UNet在去噪时可以"看到"实例应该长什么样，避免了凭空生成导致的纹理不一致。

**Q: CLIP图像引导的跨注意力机制？**

1. 实例图像 → CLIP ViT-L/14 → 实例特征F_obj (N×512)
2. F_obj通过Linear投影为K、V
3. UNet中间层的特征图作为Q
4. Cross-Attention: Q×K^T/√d → attention weights → 加权V
5. **掩码约束**：attention weights只在实例对应的2D位置区域内有效

掩码约束是关键——防止实例语义"泄漏"到背景区域。比如一辆红色车的特征不应该影响背景天空的生成。

**Q: IROS 2026审稿人可能的追问？**

1. **消融实验充分性？**
   我们做了三路消融：
   - 去掉CLIP引导：FID +3.2, 实例ID保持率-18%
   - 去掉实例VAE：FVD +5.7, 跨帧一致性-22%

   - CLIP特征相似度：同一实例在所有帧的CLIP特征方差，越低越好
   - 跟踪IoU：用目标跟踪器在生成视频上跑跟踪，计算平均IoU

## 三、驾驶场景基础视频生成模型（SVD时空双路）

### 3.1 架构详解

```
输入:
  首帧图像 I₀ → VAE → z₀ (4通道潜变量)
  文本提示 → CLIP Text → text_embedding

SVD UNet (时空双路):
  ┌─────────────────────────────────────┐
  │ 空间分支:                             │
  │   Self-Attention (空间维度)           │
  │   Cross-Attention (text K/V)         │
  │                                     │
  │ 时间分支:                             │
  │   Temporal Self-Attention (帧间)      │
  │   3×3×3 Temporal Conv (局部聚合)     │
  │   可训练Timestep Embedding            │
  │                                     │
  │ AlphaBlender:                        │
  │   α = MLP(timestep, spatial_feat)   │
  │   output = α×spatial + (1-α)×temporal│
  └─────────────────────────────────────┘

条件注入:
  z₀ → 逐帧复制 → concat到每帧噪声 → 输入UNet
  (配合noise_augmentation + random_drop实现CFG训练)
```

### 3.2 必考追问 & 标准回答

**Q: 和第一个项目的关系？**

| 维度 | 第二个项目 | 第一个项目 |
|------|-----------|-----------|
| 定位 | 基础模型：解决"如何生成连贯视频" | 进阶模型：解决"如何精确控制实例" |
| 核心贡献 | 时空建模(双路Transformer+AlphaBlender) | 实例可控(CLIP+实例VAE+ReFL) |
| 时序建模 | AlphaBlender从零学习 | 继承+实例VAE时序扩展 |
| 条件注入 | 首帧通道拼接(全局) | 首帧+实例cross-attn+实例VAE(分层) |
| 训练 | 标准扩散损失 | 扩散+实例奖励联合优化 |

第二个项目是地基，第一个项目是上层建筑。面试时先介绍第二个项目解决时空建模问题，再说第一个项目在其基础上加实例可控。

**Q: AlphaBlender融合模块的原理？**

空间分支关注单帧内的空间结构（物体在哪、长什么样），时间分支关注帧间变化（运动方向、速度）。两者需要融合，但不同时间步、不同空间位置的融合比例不同：

```python
class AlphaBlender(nn.Module):
    def forward(self, spatial_feat, temporal_feat, timestep_emb):
        # 联合预测融合权重
        alpha = self.mlp(concat(spatial_feat.mean(dim=(-2,-1)), timestep_emb))
        alpha = alpha.sigmoid()  # [0, 1]
        # 逐通道融合
        return alpha * spatial_feat + (1 - alpha) * temporal_feat
```

关键观察：
- 早期时间步(t大)：alpha偏向时间分支（整体布局还没确定，空间细节不重要）
- 晚期时间步(t小)：alpha偏向空间分支（布局已定，需要精化纹理）
- 运动区域：alpha偏向时间分支（帧间变化大）
- 静止区域：alpha偏向空间分支（帧间几乎无变化，空间细节更有效）

**Q: "折返"周期策略是什么？**

SVD默认4帧一组（3帧+1帧temporal attention），position ID从0开始单调递增。当视频超过4帧需要多组自回归拼接时，后续组的position ID超出训练范围，模型性能骤降。

折返策略：
```
组1: position_id = [0, 1, 2, 3]
组2: position_id = [0, 1, 2, 3]  (折返回0，而非[4,5,6,7])
组3: position_id = [0, 1, 2, 3]  (继续折返)
```

本质是让position embedding形成周期信号，模型始终在训练见过的位置范围内工作。效果：25帧视频的FID比线性递增position ID改善了4.2。

**Q: 首帧条件注入为什么用通道拼接而不是cross-attention？**

实验对比：

| 方案 | FID | FVD | 训练稳定性 |
|------|-----|-----|-----------|
| Cross-attention | 9.8 | 55.3 | 不稳定(需careful LR调参) |
| 通道拼接 | **7.5** | **49.1** | 稳定 |

Cross-attention：首帧VAE编码后作为K/V，噪声潜变量作为Q。灵活性高但训练不稳定——因为首帧信息需要通过attention间接传递，梯度路径长。

通道拼接：首帧VAE编码后沿通道维复制拼接到每帧噪声潜变量。信息直接可用，梯度路径短，训练更稳定。

对于首帧这种**强条件**（每一帧都需要参考首帧），通道拼接更直接有效。CLIP引导用cross-attention是因为实例条件是**稀疏条件**（不是每帧、每个位置都有实例），cross-attention更灵活。

**Q: noise_augmentation + random_drop是什么？**

训练时：
1. 对首帧潜变量z₀添加高斯噪声（noise_augmentation，σ=0.1~0.5随机）
2. 以概率p=0.1随机丢弃首帧条件（random_drop，即z₀替换为全零）

推理时：
1. 不加噪声增强，不丢弃
2. 同时做条件生成(有z₀)和无条件生成(无z₀)
3. 最终输出 = 无条件 + guidance_scale × (条件 - 无条件)

这就是**Classifier-Free Guidance (CFG)**的实现。训练时学习"有条件"和"无条件"两种模式，推理时通过guidance_scale控制条件强度。

**Q: Bounding Box下采样器的工作原理？**

```python
class BoxDownsampler(nn.Module):
    def forward(self, boxes_3d):
        # boxes_3d: [B, T, N, 6] (x, y, z, w, h, d)
        # 1. 投影到2D: 根据相机内参投影为2D box
        # 2. 渲染为特征图: 每个box渲染为8×8的one-hot map
        # 3. 卷积编码: Conv2d → 降采样到UNet所需的分辨率
        # 4. 通道维拼接: 与UNet卷积输入融合
        return box_features  # [B, T, C, H/8, W/8]
```

关键设计：
- 不是简单的坐标拼接（那会丢失空间信息），而是渲染为特征图后卷积编码
- 空间位置通过2D渲染隐式编码，比直接输入(x,y,w,h)更符合卷积网络的工作方式
- 与UNet的融合方式是**通道维加法**（而非拼接），因为Box特征是辅助条件而非主输入

**Q: 下游感知模型性能提升10%-20%怎么衡量的？**

```
实验设置:
- 基线: 仅用真实数据训练3D检测模型(BEVFormer)
- 实验: 真实数据 + 生成数据联合训练
- 评估: nuScenes验证集上mAP/NDS指标

结果:
- 常见场景(白天城市道路): mAP提升5%-8%
- 长尾场景(夜间、雨天、罕见车型): mAP提升15%-20%
- 整体加权: 10%-20% (按业务方定义的权重: 长尾场景权重更高)

为什么长尾提升更大？
真实数据中长尾场景极少(如夜间卡车切入)，模型对这些场景泛化差。
生成数据可以定向补充长尾场景，效果显著。
而常见场景真实数据已足够，生成数据的边际收益小。
```

**Q: MCP协议详细解释？**

MCP（Model Context Protocol）是Anthropic提出的Agent工具调用标准协议：

```
┌──────────┐    stdio/HTTP     ┌──────────┐
│  MCP      │ ←─────────────→  │  MCP      │
│  Client   │                  │  Server   │
│  (LLM)    │                  │  (工具)    │
└──────────┘                  └──────────┘

三种能力:
1. Tools: 可调用的函数(如ubm-schema-sync)
2. Resources: 可读取的数据(如schema文件)
3. Prompts: 预定义的提示词模板

调用流程:
1. Server启动 → 注册tools/resources/prompts
2. Client连接 → 发现可用能力
3. LLM推理 → 决定调用tool_use
4. Client转发请求 → Server执行 → 返回结果
5. LLM继续推理 → 生成最终回答
```

SceneSQL中的MCP应用：
- ubm-schema-sync注册为MCP tool
- LLM识别到用户说"schema需要更新"→ 调用tool
- tool执行git diff → label_id提取 → 母表更新 → 派生
- 返回同步报告 → LLM告知用户更新了哪些内容

**Q: RAG vs Fine-tuning vs Prompt Engineering，你怎么选？**

```
决策树:
1. 领域知识是否频繁更新？
   → 是: RAG（知识库可热更新，无需重训练）
   → 否: 进入2

2. 任务是否有固定模式/模板？
   → 是: Prompt Engineering + 模板（零成本，最可控）
   → 否: 进入3

3. 基座模型是否缺少领域知识？
   → 是: LoRA/DoRA微调（注入领域知识）
   → 否: Prompt Engineering + Few-shot

4. 训练数据是否足够(>1K条)？
   → 是: 全参数微调
   → 否: RAG + LoRA混合

SceneSQL选了RAG+Prompt Engineering:
- Schema频繁更新 → RAG
- SQL模式固定 → Prompt模板
- 训练数据不足 → 不微调
```

### 4.2 扩散模型方向

**Q: SVD和Stable Diffusion 1.5/2.1的核心区别？**

| 维度 | SD 1.5/2.1 | SVD |
|------|-----------|-----|
| 输出 | 单帧图像 | 多帧视频(14帧) |
| UNet额外层 | 无 | Temporal Attention + Temporal Conv |
| 训练数据 | LAION图像 | 视频数据集 |
| 条件 | 文本/图像 | 文本+首帧+运动信号 |
| 采样步数 | 20-50步 | 25-40步 |
| 潜空间 | 4通道 | 4通道(同SD) |

SVD的UNet在SD的基础上，每个ResBlock后加了Temporal Attention层和3D卷积层。这是视频生成的关键——让模型理解帧间关系。

**Q: CFG（Classifier-Free Guidance）原理？**

训练阶段：
- 以概率p(通常0.1-0.2)丢弃条件（文本/首帧置空）
- 模型同时学习"有条件生成"和"无条件生成"

推理阶段：
```
ε_θ(z_t, c)     # 条件预测（有文本/首帧）
ε_θ(z_t, ∅)     # 无条件预测（条件置空）

# CFG组合:
ε_final = ε_θ(z_t, ∅) + s × (ε_θ(z_t, c) - ε_θ(z_t, ∅))

s = guidance_scale (通常7.5-12.5)
```

s越大：生成越贴合条件，但多样性下降、可能过饱和
s=1：退化为普通采样（无条件项消失）
s<1：降低条件影响（很少用）

**Q: FID和FVD的计算方式？**

**FID (Fréchet Inception Distance):**
1. 生成N张图像 → InceptionV3提取2048维特征
2. 真实N张图像 → InceptionV3提取2048维特征
3. 分别拟合为多元高斯分布: N(μ_gen, Σ_gen), N(μ_real, Σ_real)
4. FID = ||μ_gen - μ_real||² + Tr(Σ_gen + Σ_real - 2(Σ_gen·Σ_real)^½)
5. 越低越好，FID=0表示两分布完全一致

**FVD (Fréchet Video Distance):**
1. 用I3D（而非Inception）提取视频级特征（包含时序信息）
2. 同上拟合高斯分布 → 计算Fréchet距离
3. FVD同时衡量单帧质量和时序连贯性
