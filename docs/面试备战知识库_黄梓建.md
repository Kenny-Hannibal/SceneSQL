## 一、SceneSQL：面向自动驾驶场景挖掘的Agentic NL2SQL系统

### 1.1 架构全景

```
用户自然语言
    ↓
Round1: ConceptRouter (概念路由)
    ├── concept_groups.yaml → NL概念→tag_name映射
    ├── schema_dictionary.yaml → 字段语义描述（2228行）
    └── LLM仅做分类：识别用户涉及哪些概念 + 组合方式
    ↓
Round2: BlockAssembler (SQL拼装)
    ├── 12种CTE Block (YAML定义)
    ├── 68种Recipe (Block编排序列)
    └── 参数化填充 → 100%语法正确的SQL
    ↓
执行 → SQLite → 结果
    ↓
Self-Correction Loop
    ├── SQL报错 → 错误信息回注Prompt → LLM修正 → 重新执行
    └── 多模态校验 → Vision模型看结果截图 → 语义判断是否正确
    ↓
前端展示: AgentPanel对话 + SqlEditor审查 + VideoPlayer视频回放
```

### 1.2 必考追问 & 回答

**Q: 为什么不用端到端LLM直接生成SQL？**
端到端生成有三个致命问题：
1. 语法错误率高——LLM生成的SQL经常有表名拼错、JOIN条件缺失等低级错误
2. 复杂多表JOIN场景下准确率骤降——30+表、200+字段的Schema，LLM容易搞混字段归属
3. 不可控——同样的query每次生成不同SQL，无法保证稳定性

两阶段架构把"理解意图"和"生成代码"解耦：Round1是分类任务（准确率天然高），Round2是模板拼装（语法100%正确）。

**Q: Block和Recipe的关系？具体例子？**
Block是可复用的CTE片段（如`ego_speed_analysis`、`event_extraction`、`duration_filter`），每个Block有自己的参数化槽位。Recipe是Block的编排序列，比如"跟车过近"场景的Recipe：
```
Recipe: cutin_too_close
  Blocks:
    1. ego_baseline        — 取ego速度/加速度基线
    2. dynamic_obj_filter   — 筛选前车(纵向距离<50m)
    3. event_extraction     — 提取cut-in事件段
    4. duration_filter      — 过滤持续时间<3s的短事件
    5. range_tag_join       — 关联range_tag标签
```
新增场景只需写Recipe YAML，不需要写Python代码。

**Q: Self-Correction怎么做的？具体纠错逻辑？**
第一层：**语法纠错**——SQL执行报错（sqlite3.OperationalError），把error message + 原SQL一起回注Prompt，让LLM修正。常见修正是表名拼错、列名不存在、括号不匹配。
第二层：**语义纠错**——SQL能执行但结果可能不对。用多模态模型（Kimi Vision）看查询结果的前N行截图+SQL语句，判断"这个SQL是不是在回答用户的问题"。如果判断为否，给出修正建议。

**Q: MCP Skill是什么？怎么触发的？**
MCP（Model Context Protocol）是一种Agent工具调用协议。我注册了一个`ubm-schema-sync`工具，当用户说"schema需要更新"或"上游代码变了"时，LLM通过MCP调用这个工具：
1. 脚本读取data_mining仓库的git hash
2. 与上次同步记录的hash对比
3. 如果有变更，提取新增label_id（5种策略扫描源码）
4. 自动更新schema_master_raw.yaml母表
5. 自动派生schema_structure.yaml和schema_dictionary.yaml
6. LLM下次生成SQL时自动使用最新的Schema

5种提取策略：
| 策略 | 扫描目标 | 提取内容 |
|------|----------|----------|
| 1 | `op_*.py` | `label_id = "TAG_NAME"` 显式声明 |
| 2 | `op_*.py` + `user_workspace/` | `CASE WHEN ... THEN "TAG_NAME"` SQL重命名 |
| 3 | `tag_map.py` refDictEn | 车端行为标签(64个) |
| 4 | 重构后的算子函数 | 函数签名中的label名称 |
| 5 | `_build_event_info(..., "TAG_NAME")` | 事件构造调用 |

**Q: Schema-Aware Prompt是怎么做的？为什么不直接把所有表结构塞给LLM？**
全量Schema有2200行YAML，直接塞给LLM会：
1. 超出上下文窗口（8K+ tokens）
2. LLM被无关信息干扰，准确率下降
3. Token成本高

做法是：概念路由识别出用户涉及的概念（如"路口""掉头"），只注入这些概念相关的表和字段定义。比如用户问"掉头场景"，只注入range_tag表+static_link表+ego表的link_turn_type字段，而非全部30+表。

**Q: 68个Recipe具体覆盖哪些场景？**
按类别分：
- 路口类：直行过路口、左转、右转、掉头、红绿灯路口（15+ Recipe）
- 变道类：cut-in、cut-out、ego变道、被超越（12+ Recipe）
- 跟车类：跟车过近、前车急刹、前车加速（8+ Recipe）
- 冲突类：横穿、鬼探头、逆行（10+ Recipe）
- 道路类：匝道进出、服务区、收费站（8+ Recipe）
- 复合类：路口+变道、匝道+跟车等组合场景（15+ Recipe）

**Q: 多模态校验具体怎么做？**
SQL执行后取前20行结果，用前端渲染为HTML表格截图，发送给Vision模型（Kimi Vision），Prompt为"这段SQL的查询结果是[结果截图]，用户原始问题是[问题]，判断SQL是否正确回答了问题，如果不正确请指出问题并给出修正建议"。

**Q: 和传统NL2SQL（如DIN-SQL、C3SQL）的区别？**
| 维度 | 传统NL2SQL | SceneSQL |
|------|-----------|----------|
| 目标 | 通用数据库查询 | 领域特定场景挖掘 |
| Schema规模 | Spider: <10表 | 30+表, 200+字段 |
| SQL复杂度 | 单表/简单JOIN | 多层CTE + gaps-and-islands |
| 生成方式 | 端到端生成 | 两阶段路由+拼装 |
| 纠错 | 无 | Self-Correction + 多模态校验 |
| Schema维护 | 手动 | MCP Skill自动同步 |

### 1.3 需要准备的技术细节

- **concept_groups.yaml**结构：concept_name → nl_variants + query_table + tag_names + tag_patterns
- **schema_dictionary.yaml**结构：tables.{table_name}.columns.{col_name}.description + enum_values
- **Block YAML**结构：name、sql_template（带{{param}}槽位）、param_schema
- **Recipe YAML**结构：recipe_name、blocks序列、variant_config
- **-1前向填充逻辑**：ego_static_map_link_id=-1时，连续≤2帧用前帧有效link_id补，>2帧保持-1
- **gaps-and-islands**：SUM(CASE WHEN prev_val != cur_val THEN 1 ELSE 0 END) OVER (ORDER BY ts) → seg_id → GROUP BY seg_id

## 二、实例可控驾驶视频生成

### 2.1 必考追问 & 回答

**Q: 和DriveDreamer-2、GenAD的区别？**
DriveDreamer-2是基于BEV布局控制的，没有实例级控制能力——它只能控制"这里有车"，不能控制"这辆车的纹理和形状"。我们的方法通过CLIP图像引导+实例VAE实现了实例级可控性。GenAD是纯BEV预测+渲染管线，没有扩散模型的渐进去噪能力，长序列生成质量差。

**Q: 实例相似度奖励反馈（ReFL）具体怎么做？**
1. 从生成视频和真实视频中裁剪出对应实例区域
2. 分别用CLIP ViT-L/14提取特征
3. 计算余弦相似度作为奖励信号
4. 在扩散时间步t∈[30,40]（接近去噪末端）联合优化奖励损失和标准扩散损失
5. 实例ID过滤：只对首帧出现的实例计算奖励，避免无关实例干扰

为什么选t∈[30,40]？早期时间步（t大）决定整体布局，修改会破坏结构；晚期时间步（t小）只影响细节纹理，奖励信号太弱。中间段是语义和纹理的最佳平衡点。

**Q: IROS审稿人可能问什么？**
- 消融实验是否充分？（我们做了CLIP/VAE/奖励三路消融）
- 实例ID保持的定量评估怎么做？（用CLIP特征相似度+IoU）
- 扩展到更长视频（>25帧）的效果？（承认有退化，这是未来工作）
- 训练成本？（20万步，8×A100约72小时）

**Q: "时空复制粘贴"VAE管道的技术细节？**
1. 对每个实例，取首帧裁剪图像
2. 根据未来帧的3D Box位置，用仿射变换将实例图像放到对应位置
3. 沿时间轴复制扩展，形成4D实例条件张量
4. 用VAE编码为条件潜变量
5. 与噪声潜变量在通道维拼接输入UNet

这提供像素级纹理参考，解决了"车在不同帧长得不一样"的问题。

### 2.2 关键数字要记牢

- FID 7.1, FVD 48.5（nuScenes验证集）
- 较DriveDreamer-2: FID↓36.6%, FVD↓12.9%
- 训练：20万步预训练 + 1万步奖励微调
- IROS 2026接收

## 三、驾驶场景基础视频生成模型（SVD时空双路）

### 3.1 必考追问 & 回答

**Q: 和第一个项目是什么关系？**
第二个项目是基础模型——解决"如何用SVD生成连贯的驾驶视频"，核心是时空建模（双路Transformer+AlphaBlender）。第一个项目是进阶——在基础模型之上加实例级可控性（CLIP引导+实例VAE+奖励反馈）。所以第一个项目依赖第二个的时空建模能力。

**Q: AlphaBlender融合模块的原理？**
空间分支和时间分支各自输出特征图，AlphaBlender学习一个逐通道的融合权重α，输出=α×空间特征+(1-α)×时间特征。α通过一个轻量MLP从时间步嵌入和空间特征联合预测。关键：α是可学习的，不同时间步、不同空间位置的融合比例不同。

**Q: "折返"周期策略是什么？**
SVD默认4帧一组（3+1 temporal attention），position ID单调递增。当视频超过4帧需要多组拼接时，位置ID超出训练范围导致质量下降。折返策略：position ID到最大值后折返回0重新递增，形成周期信号，让模型始终在见过的位置范围内工作。

**Q: 首帧条件注入为什么用通道拼接而不是cross-attention？**
实验对比过两种方案：
- Cross-attention：首帧VAE编码后作为K/V，噪声潜变量作为Q——灵活性高但训练不稳定
- 通道拼接：首帧VAE编码后沿通道维复制拼接到噪声潜变量——更直接、训练更稳定、推理更快

对于首帧这种强条件（每帧都需要），通道拼接效果更好。CLIP引导用cross-attention是因为实例条件是稀疏的（不是每帧都有实例）。

**Q: 下游感知模型性能提升10%-20%怎么衡量的？**
用生成视频作为额外训练数据，重新训练下游感知模型（3D检测/跟踪），在真实数据验证集上评估mAP/MOTA。提升幅度因场景而异：长尾场景（夜间、雨天）提升更大，常见场景提升较小。

### 3.2 和第一个项目的对比（面试必问）

| 维度 | 第二个项目 | 第一个项目 |
|------|-----------|-----------|
| 控制粒度 | 场景级（首帧+文本+Box） | 实例级（每个物体独立控制） |
| 时序建模 | 双路Transformer+AlphaBlender | 继承+实例VAE时序扩展 |
| 训练策略 | 标准扩散损失 | 扩散损失+实例奖励联合优化 |
| 核心贡献 | 时空连贯性建模 | 实例级可控+跨帧一致性 |

## 四、通用面试题

### 4.1 LLM/AI Agent方向

**Q: 你怎么看NL2SQL这个方向？**
NL2SQL是LLM在数据领域最有落地价值的方向之一。原因：
1. 企业数据大部分在关系型数据库，自然语言查询需求强烈
2. SQL是形式语言，语法正确性可验证（不像开放式生成无法评判）
3. 有明确的评估指标（执行准确率），便于迭代优化
4. 2024-2025年BIRD、Spider等benchmark持续刷新，学术热度高

挑战在于：复杂Schema+多表JOIN+领域术语，纯端到端生成不够可靠，所以两阶段/Agentic方案是趋势。

**Q: MCP协议你了解多少？**
MCP（Model Context Protocol）是Anthropic提出的Agent工具调用标准：
- Server暴露tools/resources/prompts三种能力
- Client（LLM）通过stdio或HTTP连接Server
- 工具调用流程：LLM生成tool_use → 客户端转发给MCP Server → Server执行 → 返回结果 → LLM继续推理
- 我项目中的ubm-schema-sync就是注册为MCP tool，LLM可以主动调用

**Q: RAG vs Fine-tuning vs Prompt Engineering，你怎么选？**
决策树：
1. 领域知识是否频繁更新？→ 是：RAG（知识可热更新）
2. 任务是否有固定模式？→ 是：Prompt Engineering + 模板
3. 基座模型是否缺少领域知识？→ 是：LoRA微调注入
4. 数据量是否足够微调？→ 不足：RAG + Few-shot Prompt

SceneSQL选了RAG+Prompt Engineering，因为Schema频繁更新、SQL模式固定、训练数据不足。

### 4.2 扩散模型方向

**Q: SVD和Stable Diffusion 1.5/2.1的区别？**
SD是图像生成模型（单帧），SVD在SD基础上加了时间维度的attention和3D卷积，支持视频生成。SVD的UNet比SD多了temporal attention层和temporal conv层。

**Q: CFG是什么？为什么重要？**
Classifier-Free Guidance：训练时以概率p丢弃条件（条件置空），推理时同时做条件生成和无条件生成，最终输出=无条件+guidance_scale×（条件-无条件）。guidance_scale越大，生成越贴合条件但多样性下降。

**Q: FID和FVD的区别？**
FID（Fréchet Inception Distance）：单帧质量指标，用Inception特征计算生成图像和真实图像分布的距离
FVD（Fréchet Video Distance）：视频质量指标，在FID基础上加入时序维度，用I3D特征替代Inception特征

### 4.3 行为面试

**Q: 你在广汽最大的技术挑战是什么？**
"数据挖掘的SQL编写效率极低——每个场景需求都要工程师手写几百行CTE SQL，而且上游算子频繁迭代导致Schema经常过期。我设计了SceneSQL系统解决这两个问题：两阶段架构把SQL编写从手写变成自然语言描述，MCP Skill把Schema维护从人工变成了自动化。"

**Q: 你的职业规划？**
"深耕AI+数据方向，短期在NL2SQL/Agentic AI持续深耕，中长期希望将多模态理解（视频生成+视觉校验）和数据分析（NL2SQL）打通，做端到端的智能数据分析平台。"
